# Contributing to Trip

Open `trip.xcodeproj` in Xcode 27 and select the shared `trip` scheme. The local
TripKit package resolves from `Packages/TripKit`; there are no remote packages,
secrets or servers required for a local source change. Localization accessors are
generated by the checked-in Python tooling; feature scaffolding is optional.
Start with `AGENTS.md`, then the guide for the area you will change below.

The product baseline is iOS/iPadOS 27.0+. Use [skill ownership and selection](docs/Skills.md)
to choose Trip-specific guidance and relevant installed global framework topics.
Reusable global skills and their maintenance tools stay outside this repository.
Verify current SDK declarations; 27.1+ additions still need availability gates.

The single global `app-development` skill owns reusable engineering guidance.
Trip retains its [applied review](docs/reviews/apple-guidance-2026-10-24.md) and product contracts;
private historical archives are separate from the shareable global skill.
Normal source checks and scaffolding require no personal global skill installation.
Before adding guidance, extend an existing global skill for common techniques;
keep only Trip contracts, paths, product choices, and commands in project skills.

## Repeatable workflow

Use [Development](docs/Development.md) for task briefs, feature scaffolding, AI
context, and review. [Dependencies](docs/Dependencies.md) describes production and
preview composition; [Testing](docs/Testing.md) describes future test placement.
Architecture decisions live in [docs/decisions](docs/decisions/README.md).

```sh
python3 scripts/workspace.py list
python3 scripts/workspace.py locate trip/Features/Trips --json
python3 scripts/workspace.py context Trips --json
```

## First change

1. Run `bash scripts/check.sh` from the repository root for the source baseline.
2. Choose the owning area below. Follow its entry view → controller → model.
3. Start from a named same-file preview; use local fixtures for component work.
4. Put behavior in a model, user actions in a struct controller, and UI in a view.
5. Run `bash scripts/check.sh` again and describe the affected behavior and checks.

The scripts honor an explicit `DEVELOPER_DIR`. When macOS selects Command Line
Tools, they use `/Applications/Xcode.app` or `Xcode-beta.app` for that process only.
For Xcode installed elsewhere, set `DEVELOPER_DIR` to its `Contents/Developer`.
No script changes the global `xcode-select` setting.

## Work in parallel

Developers can take Explore, Trips, and Directions independently.
Additional developers can own MapEngine, storage, generation, or tooling. This is
an ownership plan; source separation does not guarantee conflict-free integration.

Each work item should identify its owned directories and the contract it needs.
If contracts stay unchanged, implement and preview inside that area without
editing AppModel or another feature. Change the relevant feature's fixture file,
not the central preview factory, unless adding shared data.

For a cross-feature requirement, agree on a small callback/value contract first.
One change owns the contract and AppModel wiring; feature changes consume that
contract. Put reusable values in TripDomain and workers in the corresponding
package. Do not pass an entire feature model into a sibling's controller.

`scripts/architecture/app-ownership.json` rejects forbidden direct feature references and
package imports. `Packages/TripKit/modules.json` defines the package graph.
Shared contract and manifest edits deserve coordination because they affect
several consumers. Xcode uses synchronized source folders, so ordinary new Swift
files do not need competing `project.pbxproj` edits.

Use separate branches/checkouts for simultaneous development. Preserve existing
changes, avoid repository-wide formatting, and keep each commit focused on one
behavior or boundary. Do not publish or push unless requested.

## Verification

`bash scripts/check.sh` runs architecture, workspace-reference, compiler-policy, source-size, preview-presence,
controller-storage, UIKit, and diff-whitespace checks. It does not build the app,
run package tests, or benchmark algorithms. The dependency checker is a lexical
guard; successful compilation is still needed to verify types and imports.

When editing the checker itself, run its focused regression checks:

```sh
python3 -m unittest discover -s scripts -p test_architecture.py
```

Builds and benchmarks run only when requested for agent tasks. Choose the smallest
relevant build; package commands compile for the host Mac, and the app command
uses a generic iOS Simulator. Neither establishes visual or device behavior.

```sh
bash scripts/build.sh TripLocalization
bash scripts/build.sh TripDomain
bash scripts/build.sh MapEngine
bash scripts/build.sh TripRouting
bash scripts/build.sh TripStorage
bash scripts/build.sh TripIntelligence
bash scripts/build.sh app Debug
```

Use `Release` as the second argument for optimization. Keep `.build/modules` and
`.build/xcode` for incremental caching. For requested algorithm checks, use
`bash scripts/performance.sh`; routing package checks are documented in
[DIRECTIONS.md](DIRECTIONS.md). Native map/sheet changes also need device or Canvas
verification for gestures, keyboard, attribution, large text, and Reduce Motion.

A review should state what changed, why it belongs in this owner, whether a
contract changed, and exactly what was verified. Preserve Swift 6 concurrency,
iOS 27 deployment, stable identities, and data migrations. A source audit is not
proof of successful compilation, and compilation is not visual verification.
